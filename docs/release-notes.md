## v3.2.2 — 修自配 Anthropic 的 404，并补运行期兜底

**现象**：`agent_delegate` 启动 `yokos-beichenapi-anthropic/claude-opus-5-5` 成功，但子代理运行即失败（`404 page not found`，无任何提示）。

**根因**：profile 里该 provider 的 `baseURL` 写成 `https://api.beichenapi.com/v1`，而适配器会再拼 `/v1/messages` → 实际请求 `/v1/v1/messages`。
实测：`/v1/messages` 返回 401（路径对、只缺 key），`/v1/v1/messages` 返回 404。

**改了什么**
- `baseURL` 改成 `https://api.beichenapi.com`（改前备份 profile）
- `agent_delegate` 返回 `fallbackRoute`：运行期失败时主模型直接拿它重派官方，并告知「自配失败，已用官方兜底」

**限制**：预检只保证配置可解析，不保证网络连通；运行期失败只能靠 `fallbackRoute` 重派，工具自己不会等待子代理结果。

## v3.2.1 — 修：推理等级把自配模型误判成不可用

**现象**：性能档自动挑到 `yokos-beichenapi-anthropic/claude-opus-5-5` 时，预检报 `does not support reasoning effort "high"`，随即回落官方——看起来像"自配 API 挂了"，其实是 CT 自己硬编码了推理等级。

**改了什么**
- 能力探测时采集模型真正声明的 `efforts`（`resolveModelInfo`）；没声明就**不传** `reasoning_effort`
- 有声明时：性能档取最高一档、效率档取默认档；自动挑出的等级现在真的会传给子代理
- 预检失败若是推理等级问题：先去掉 `reasoning_effort` 重试自配，仍失败才回落官方

**影响面**：只改 `agent_delegate` 的挑路与预检；已存的档位/白名单/官方工具不变。

## v3.2.0 — 三后端 + 自配故障自动回退

**改了什么**：`agent_delegate` 支持 `backend: spawn | claude-code | codex`；自配 API 出意外时自动回退官方并提醒。

**三后端**
- `spawn`（默认）：模型走 `agentOptions`，按档位/领域自动挑，**运行时就能切**
- `claude-code` / `codex`：走各自 CLI 的运行时（文件编辑、shell、代码理解），**模型由 CLI 配置决定**——这两个后端不接运行时模型参数，`agent_delegate` 也不再假装能切

**回退链**
1. 自动挑到非 `deepseek-*` 的 provider → 先 `llm.resolveCallConfig` 预检；
2. 预检失败 / 子代理启动失败 → 回退官方 route 重试一次；
3. 返回 `fellBack: true` + `note`，文本第一句「⚠️ 已回退」；
4. CLI 后端起不来 → 回退 `spawn` + 官方。

**限制**
- `claude-code` / `codex` 要各自 CLI 已登录；没登录会在启动阶段失败并回退
- 回退不改变你的配置，只保证这次任务能跑完；下次会重新按计划挑

## v3.1.0 — 当前会话也能用自配 API：`agent_delegate`

**改了什么**：官方 `subagent` 的模型白名单在会话创建时快照，改配置只对新会话生效。新增 `agent_delegate` 工具走 provider 层，**当前会话立刻可用**，含你自配的 API。

**怎么用**
- `agent_delegate({prompt, description, module})`：模型按当前「代理」档位与领域自动挑（executor→code / review、counter→reasoning / research→longContext）
- 也可显式给 `provider` + `model` + `reasoning_effort`，原样透传
- `module:"counter"` 会自动避开主模型 provider（拿不到主模型信息时标 `unknown`，不谎报隔离）

**代价（重要）**：它把 route 放进子代理 `agentOptions`，**绕过宿主 allowedModels**，因此没有额度护栏。批量派活前先看成本；官方 `subagent` 仍按白名单走，两者并存。

**限制**
- 需要宿主有 `subagents` 服务（DSH 自带）；缺失时工具直接报错，不静默
- 不自动装 codex / claude-code 后端；只走 `spawn`
- 白名单对官方工具的老限制没变：要官方工具也用自配模型，仍得改 profile + 新开会话

## v3.0.0 — 第五模式「代理」+ 子代理模型路由 + 对抗 v2

**改了什么**：档位条从四模式变五模式，多一个可叠加的「代理」开关；检索少一档；对抗审升级为独立模型 + 三查。

**代理（新）**
- 开：`clarify_tier.agent` 给 `planId` 与各模块的 `provider/model`，模型据此派子代理；再选「效率（性价比）/ 性能（绝对质量）」
- 关：`{on:false}`，不指定模型、不改白名单，等于官方默认
- 它是策略开关，不接管官方 `subagent`；不改宿主白名单就改不了「能不能用某个模型」——`list_subagent_models` 对白名单外的 provider 会直接报 `not allowed for this Session`

**模型怎么挑**
- 读宿主注册表（含你自配的 API），按能力基线（族 × 领域）打分，同分看上下文窗口
- 自动更新的是「有哪些模型」，「谁更强」不会自动知道；未知族标 `unknown 5 分`
- 对抗档强制避开主模型 provider；只能同族时降级为「隔离度：中」

**检索**
- 三档改两档：增量 / 全量。「本地」不再单独占一格——**关掉开关就是本地**
- 旧状态里的 `off` 自动迁移成 `increment`（high）

**对抗 v2**
- 新增技能 `counter-audit`：权威性（L1–L4）/ 真实性（逐条回源）/ 全面性（原六轴 + 数据/引用/逻辑）
- 新增工具 `verify_claims`：机械核对断言与来源（文件行号 / URL 域名 / 命令片段），只证明「有对应源」，不证明源真实
- 报告头固定写 `审者模型 · 隔离度 · planId`，不许用主模型自审冒充隔离审

**状态**：schema 8 → 9（补 `agent`）；v7 跨两级迁移、v8 单级迁移，迁移前留 `.bak`。

**限制**
- 子代理白名单是会话创建时的快照：改了配置只对之后新建的会话生效
- 注册表里只有同族模型时，效率/性能两档可能给出相同 route（不是 bug，是可选模型不够）
- 代理关 ≠ 收回权限：白名单扩容是一次性的

## v2.3.0 — 思考强度落到清单：歧义点 / 覆盖轴 / 逆向

**改了什么**：`clarify_tier` 不再只回一个档名，而是随档位发三张清单，模型据此决定「问什么、看多全、怎么反推」。

**三张清单**：

- **歧义点**（严格 2 条 / 极致 3 条）：目标与验收能不能一句话说清；不可逆与外部动作（推送 / 发布 / 改设置 / 删除）谁批准、怎么回滚；范围与取舍（不做什么、代价是什么）。只有**答案会改变执行**的才弹窗问，能自己查证的不占提问额度。
- **覆盖轴**（严格 3 条 / 极致 6 条）：正常路径、边界与空值、失败与回滚；极致再加依赖与副作用、成本与性能、后续与可维护。逐轴一句结论，未涉及的写「Z」。
- **逆向**（严格 1 条 / 极致 3 条）：pre-mortem（假设已失败，倒推原因）；极致再加反证（什么证据会推翻结论）与反例（触发条件 / 后果 / 检查方法）。

**循环模式不再短路**：此前循环档固定返回 `tier: "off"`、工具文案写「不叠加思考档」，于是循环档里从不提问——2.2.1 的 GitHub About 带着「一框三模式」发了两版没人发现，就是这条的直接后果。现在轻量 / 交付 / 极致 同档位映射成 常规 / 严格 / 极致，`think.source` 标 `loop`；`forge_level` 同样带 `think`。

**范围**：状态 schema、`/state` 字段、客户端节点与配色都没变；变的是两个工具的返回结构与文案。`think` 里 `probes / axes / reverse` 是可执行清单，`confirm` 是要报的确认点个数，`ask` 是提问口径。新增 3 项测试，共 86 项。

## v2.2.1 — 循环模式下「检索」恒天蓝

**改了什么**：`检索` 开关和它展开的三格（本地 / 增量 / 全量）不再跟着模式换色——思考、循环都是天蓝 `#3a9ad9`。循环开关仍绿、对抗开关仍红；循环 + 对抗同开时只有等级条转橙。

**为什么坏**：循环的换色规则原先写通用选择器 `.dct-cell[data-on='1']:not(.dct-counter)`（特异性 0,5,0），压过检索的 `.dct-routecell / .dct-route-toggle`（0,3,0）——只要在循环模式，检索那两处也被染绿。使用说明与 README 写的却是「检索常驻天蓝」，实现和文档不一致。

**改法**：循环换色收窄成 `.dct-cell[data-level][data-on='1']`，只认等级条。收窄后循环格原先靠这条通用规则显绿，它自己的 `.dct-mode[data-on='1']`（0,2,0）会输给紫（0,3,0）而变紫，所以升到 `.dct-root .dct-cell.dct-mode[data-on='1']`（0,4,0）——与源序无关，不再靠「先写谁」。

**范围**：纯前端样式。状态 schema、`/state` 字段、`clarify_tier` / `forge_level` 返回值、DOM 节点与文案都没变。四态取色用 headless Chrome 核对：循环=绿、检索=天蓝、循环+对抗同开=橙绿红蓝四色并存、思考=紫+天蓝。新增 1 项守卫测试，共 81 项。

## v2.2.0 — 第四个模式「检索」（可叠加）

**改了什么**：主条最右多一格 `检索`，开启后最左多出三格 `本地 / 增量 / 全量`；思考档、循环档、对抗开关原样保留，四者互不覆盖。

## v2.1.0 — 循环 + 对抗 同开：等级条转橙

**改了什么**：`循环` 与 `对抗` 同时亮起时，左边三格的选中格由绿 `#66ae7c` 转橙 `#cf8a4a`。循环开关保持绿、对抗开关保持红，橙只落在等级格上——「边磨边审」这个组合状态在一条 20 像素高的控件上一眼可辨。

**为什么不是色值平均**：绿与红直接平均是 `#a0967d`（土黄），既不橙也发灰；橙色取同亮度、同饱和度的暖橙，避免它成为整条最亮的一格。

**实现**：橙收在 `--dct-mix` 变量里，与另外三色同一处定义；根节点多一个 `data-mix`，只在 `mode=loop && counter=true` 时为 `1`，CSS 只认这一位。

**范围**：纯前端样式。状态文件、`/state` 字段、`clarify_tier` / `forge_level` 的返回值都没变；单独循环或单独对抗不变色。新增 3 项守卫测试，共 65 项。

## v1.7.0 — 对抗审：每轮改动都问一句「万一」

**动机**：循环里的独立评审管「现在错没错」，管不了「换个环境/换种用法会不会错」。沉没成本最贵的一次事故（认领信号被自己污染，连修三个版本）就属于后者。

**做法**：新增技能 `counter-review`。每轮评审后，按六轴场景矩阵（版本/环境、机器状态、用户用法、数据形态、时序、极端量）对本轮改动逐条拷问；每条攻击必须写清 `隐患 | 触发条件 | 后果 | 检查方法`，缺一项直接作废；结论三选一——接受（挂缺陷号）、驳回（给证据）、转边界（写进已知边界）。

**预算**（防杠精化）：轻量档关；交付档只在收敛轮、≤3 条；极致档第 2 轮起每轮、≤5 条；连续两轮零新增即「泛化收敛」停止。

**开关**：`forge_level` 返回新增 `counter` 字段（enabled / maxAttacks / scope / onlyFinalRound / fromRound），由 `COUNTER_PLAN` 统一给值，改档位只改一处。

**与既有能力的分工**：`clarify-needs` 的对抗自检/复审在动手前审方案；本技能在循环里审改动；两者共用一套矩阵与判定。

**验证**：58 项测试（新增 3 项）；`loop-forge` 已接入（评审后、修之前）；技能已 junction 进两套 DSH。

**命中演练**：让一个不看结论的子代理只看「方法 + 三个改前状态」，对本项目 1.4.2 假日志 / 1.5.0 认领污染 / 1.6.0 过度设计出攻击，15 条里 **3/3 命中已知根因**（明细见 `skill/counter-review/docs/method.md` 第三节）。

## v1.5.3 — 认不准就不碰桥

**问题**：两套 DSH 同开、而本会话还没被任何一方的工具写过时，客户端只能「先用探测到的端口」——于是本应用的控件可能显示另一套的档位。1.5.1/1.5.2 保证不写坏对方文件、5 秒后自愈，但那几秒仍然读到了别人的值。

**修法**

- `scanInstances()` 一次扫清「有几套实例、各自认不认识本会话」。
- 判定：有 owner → 切过去；**只有一套** → 直接认（没有连错的可能）；**两套以上且都没认领** → 不读、不写、不连 SSE，只显示本地值并带 `!`，点击记账，认准后补写一次。
- 本地值天然属于本应用（localStorage 按 app 分区），所以认不准的阶段也不会串。

**顺带修的**：挂载时 `pull()` 调了两次，导致两条轮询链并发、轮次翻倍（12 轮实际约 60 毫秒烧完）；加单飞保护。

**验证**：55 项测试（新增 2 项：单实例直接认领、两套都不认领时不连 SSE 不写桥且认领后补写）。

## v1.5.2 — 未认领时定时重试

**问题**：刚打开窗口时，本轮的 `clarify_tier` 还没落盘，两套实例都不认识这个会话，客户端只能先用探测到的端口——可能是另一套的。原来只等「窗口聚焦」才复检，用户盯着页面不动就一直连错。

**修法**：认领失败时按 `CONFIG.ownerPollMs`（默认 5 秒、最多 12 轮 ≈ 1 分钟）自动重试，认领上立即停止。实测场景：官方 DSH 刚打开时 SSE 连到了 NEXT 的桥，现在最多 5 秒自己切回自己的端口。

**不变的部分**：未认领期间的点击只写本地（1.5.1 起不会污染对方文件），认领后以宿主值为准。

**验证**：53 项测试（新增 1 项：无人认领 → 轮询 → 认领成功并停止）。

## v1.5.1 — 认领信号只认工具写的

**问题**：1.5.0 用「本实例状态文件里有没有这个会话」作认领依据。但客户端自己也会写这个会话——一旦误连到另一套实例，点一下档位就把会话写进对方文件，两个实例都「认识」它，信号被自己污染，再也分不出谁是谁。

**修法**

- 每个会话多一个 `owner`：客户端 POST 标 `client`，工具落「本轮快照」时标 `tool`；owner **只升不降**。
- `knownSession` 只在 `owner === "tool"` 时为真——只有本实例的工具为这个会话落过盘，才算「我的」。
- 复核更及时：任何一次拉取发现 `knownSession=false` 就安排一次复核（`CONFIG.ownerCheckTtl` 节流 3 秒），不再只等窗口聚焦。

**兼容**：老状态文件没有 `owner` → 视为未认领，退化成 1.4.2 的行为（缓存 + 首个命中）；本轮第一次工具调用后自动获得认领能力。误连期间的点击不会再写坏对方文件。

**验证**：52 项测试（新增 1 项：客户端写不算认领 / 工具写后才算 / 工具认领后客户端再改档不降级）。

## v1.5.0 — 两套 DSH 同开时按「会话归属」认桥

**问题**：官方 DSH 与 NEXT 各跑一份本插件时，两个桥的 `plugin` 标记一模一样。客户端手上的 `localStorage["dsh-tier-port"]` 一旦丢失（换机、清缓存、首次打开），它会按 43871→43880 探测，可能挂到**另一套实例**的桥上——表现是控件显示/写入的档位，跟本应用工具读到的对不上。

**修法**

- `/state` 增加 `knownSession`：本实例的状态文件里有没有这个会话（会话 id 由客户端与工具两侧共用）。
- 客户端挂载时先认领：读一次当前桥的状态，若 `knownSession=false`，扫一遍端口找到 `knownSession=true` 的那个，切过去并把端口写回缓存，然后才连 SSE。
- 认领时机只有两处：挂载、窗口重新聚焦。老宿主不带 `knownSession` 时一次都不多扫，行为与 1.4.2 完全一致。

**兼容与空窗**：客户端与宿主同版本才有认领能力；单向升级退化为旧行为。刚开的对话还没被工具写过时，两边都是 `false`，此刻只能先用缓存端口，本轮第一次 `clarify_tier` 落盘后（切窗口或下次挂载）自我纠正。

**验证**：51 项测试（新增 3 项：`knownSession` 正确性、两套实例按归属切端口、老宿主不额外扫端口）。

## v1.4.2 — 端口退让的日志与 chosenPort

**问题**：两套 DSH 同开时，后启动的那套会退让到下一个端口。但同一个 `http.Server` 上重试 `listen()` 时，前一次失败那回的 listen 回调也会被一起触发，于是日志里同时出现「就绪 43871」和「就绪 43872」——43871 其实是别的实例占着，`chosenPort` 也会被短暂写错。

**修法**

- 以 `server.address().port` 为准：实际绑上哪个端口才记「桥接就绪」，其余回调直接返回。
- 单端口 EADDRINUSE 不再打「控件会退化为只读」（那句只在 10 个端口全占时才成立）；运行期错误另走「桥接错误」。

**验证**：48 项测试（新增 1 项：退让成功时「桥接就绪」只出现一次、且写的是真绑上的端口），并确认回退该修复时这条测试会红。无行为变更。

## v1.3.0 — 少一次请求，断线能自己回来

**本次改动**

- **点一次档只发一个 POST**：宿主在 POST `/state` 的响应里直接回带 `mode/level/pending/turnLocked`，客户端不再补 GET。老宿主（1.2.0 及以前）不回 `pending`，客户端自动退回「POST + GET」，行为不变。
- **端口发现退避**：一轮 10 个端口全探空后记下时间，3 秒内点击不再重扫（原来每次交互都要打 10 个 fetch）；挂载时 `pull` 与 SSE 并发要端口，改为同一时刻只跑一轮发现。
- **端口缓存会作废**：GET 拿到非 2xx（端口上是别的实例）、网络错误、SSE 彻底断开，都清掉缓存的端口，下次重新发现。原来宿主重启换了端口，客户端会一直指着旧端口。
- **SSE 断线重建**：`readyState=2` 时浏览器不再自己重连，客户端按 `CONFIG.reconnectDelay`（默认 2 秒）重建，最多 `CONFIG.maxReconnects`（默认 3）次，收到消息即重置计数。
- **诊断默认关**：不再每次启动往 `clarify-tier-debug.jsonl` 追加事件（文件不轮转）。要抓注册链路时执行 `localStorage.setItem("dsh-tier-debug","1")` 再刷新，用完删掉。
- 客户端三处重复的落值逻辑收成 `applyState()`；容器 title 由 `barTitle()` 统一生成，离线与「下一轮生效」同时成立时两句话都写。
