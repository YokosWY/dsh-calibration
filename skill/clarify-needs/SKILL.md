# 需求锚定与拷问（v4.0）

动手之前，把「要做什么 / 为什么这么做 / 做到什么算完」锚定住。
锚定强度分四档：**off 关闭 / low 常规 / high 严格 / max 极限**。off 表示不使用本技能，其余三档才是「用技能、用多深」；档位决定问多深，也决定怎么问——不再另设模式。

## 1. 四档

| 档 | 语义 | 锚定度 | **必须产出的东西** | 动手条件 |
|---|---|---|---|---|
| **off** | **关闭** | — | 无 | 技能退出，直接做 |
| **low** | 常规（默认） | 80% | 复述 + 2 确认点 + **风险提示** + **假设清单（≤3 条）** | 主路径没有分叉 |
| **high** | 严格 | **95%** | 常规 + **回滚方案 + 验收标准 + 失败分支** + **前置检查表** | 每步可执行、可退、可验 |
| **max** | 极限 | 99% | 严格 + 设计树 + **反例与代价** + **对抗自检** + **对抗复审** + **止损线** | 用户确认摘要 |

四档的差别必须**看得出**：档位越高，动手前交出的东西越硬。
**缺件即未达标**：某一档要求的产出少一件，就不算完成锚定，不许动手（补齐或降档说明）。

**提问不设数量上限**：判停看「还有没有会改变执行的未知」，不看问了几轮、几题。
一次问完当前所有缺口；问题够狠时 5 个不算多，问题没用时 1 个都嫌多。

**锚定度** = 不猜也能写出执行步骤的比例；off 不计（不走本技能）。

- **常规**：目标与禁区定死，实现放开
- **严格**：步骤、失败处理、回滚、验收
- **极限**：每条分支都有结论，没有默认假设

## 2. 定档

顺序：**用户点名 > 滑条 > 自动评分 > 默认 low**。

**滑条**：输入框工具行的档位条（插件 `dsh-clarify-tier`）写的是宿主状态。**只要 `clarify_tier` 工具存在，每轮开工前必须调用一次**——读到什么就用什么，读不到才走下面的评分。用户在滑条上拨的值优先于自动评分。

**档位靠行为体现，不写标签**（不标「档位 X」，差异体现在动作上）：

| 档 | 第一条输出的固定形状 |
|---|---|
| 关闭 | 无任何澄清语句，直接动手 |
| 常规 | 复述 + 2 个确认点（要什么 / 动哪些）+ **一句「最可能出岔子的是 X」** |
| 严格 | 常规的三样 + **回滚方案 + 验收标准 + 失败分支表** |
| 极限 | 一次弹窗问完 frontier（多题、首项推荐）→ 共识摘要 → **逐条附反例与代价 + 对抗自检** |

用户直接说「用 low / 走 high / 锚定 max / 别问了」→ 立刻采用，不算分。

自动评分（四问，30 秒）：

| 问题 | 分 |
|---|---|
| 要动 ≥2 个对象，或跨目录 / 跨应用 | +1 |
| 只给目标、没给做法 | +1 |
| 在纠结「要不要做 / 选哪条路」 | +2 |
| 不可逆（删除 / 覆盖 / 迁移 / 花钱 / 对外） | +2 |

`0 = off`（本技能退出），`1 = low`，`2 = high`，`≥3 = max`，再加三条地板：

- **只要不可逆 → 至少 high**
- **不可逆 且 在纠结方向 → max**
- **会改动文件 / 配置 / 系统的任务 → 最低 low**（off 只留给纯查询、纯只读）

### 升降档

| 触发 | 动作 |
|---|---|
| 「别问了 / 不用澄清 / 直接做 / 你自己决定」 | → **off：本技能退出**，按常规直接执行 |
| 「简单确认下 / 大概就行」 | → low |
| 「仔细点 / 这个重要 / 别搞错」 | 升一档 |
| 「拷问我 / grill 我 / 往死里问」 | → max |
| 中途发现不可逆、或影响面变大 | 至少 high，并说明为什么升 |
| 连续两轮仍在同一缺口上打转（问不出新信息） | 兜底：默认方案 + 风险 + 回滚，请回「按这个来」 |

## 3. 各档怎么做

### off · 关闭

这一轮**不走本技能**：不复述、不提问、不输出档位、不追加任何澄清性语句。
技能视为未加载——既不额外标「假设」，也不额外限制做法，按你平时的执行标准直接做完。
用户说「别问了 / 不用澄清 / 直接做」时进入 off，作用范围到本任务结束；下一个任务重新定档。

### low · 常规（默认）

复述 + 2 个确认点：**要什么**（成功长什么样）、**动哪些**（文件 / 目录 / 应用），再补**一句风险提示**：

> 最可能出岔子的是 **X**，出了我按 **Y** 处理。

缺口问完就开工，不管问了几题。主路径没有分叉即停。

**假设清单**：凡按默认处理的地方，逐条写成「假设：…」，最多 3 条并标明「错了会怎样」。超过 3 条说明该升档问清楚，不许靠假设凑数。

### high · 严格

在常规档三样（复述 / 2 确认点 / 风险提示）之上，动手前还必须交出三件：

| 产出 | 长什么样 |
|---|---|
| **回滚方案** | 出问题退回哪一步、怎么退（命令或操作），退不回来时怎么办 |
| **验收标准** | 怎么算做完，逐条可勾选（不是「看着差不多」） |
| **失败分支** | 最可能失败的 2–3 处 + 各自的处理动作 |
| **前置检查表** | 依赖在不在 / 权限够不够 / 备份做了没 / 有没有在跑的进程会撞上 —— 逐项标 ✓ 或 ✗ |

无轮次上限，五维有空白就问。动手前自检五维，任何一项空白就说明没到 95%：

| 维度 | 问自己 |
|---|---|
| 目标 | 最终要什么结果？成功长什么样？ |
| 对象 | 具体哪些文件 / 目录 / 应用 / 账号 / 工作区？ |
| 边界 | 哪些不能动？只读还是可改？哪些必须保留？ |
| 条件 | 时间、预算、凭据、正在运行的进程、不可逆风险 |
| 优先级 | 速度优先还是安全优先？出问题先保哪个？ |

**95% 判据**：能不猜地写出执行步骤，每步输入 / 输出 / 失败处理都确定，且边界、回滚、验收标准也已定死。

- 有一个判断是「我觉得应该是…」→ 不到 95%
- 有一处「出问题再看」或「做完再说」→ 不到 95%

### max · 极限

设计树 + frontier 整轮拷问（见第 5 节），在严格档三件之上再加两件：

| 产出 | 长什么样 |
|---|---|
| **反例与代价** | 每个主要分支：选它的代价是什么、什么情况下会被它害到 |
| **对抗自检** | 列出 3 条最可能错的前提，逐条找反证；找得到反证就改，找不到才算过关 |
| **对抗复审** | 换一个陌生视角（或派一个不带本会话上下文的子代理）审自己的方案，至少提 3 条反对意见，逐条回应「接受 / 驳回 + 理由」 |
| **止损线** | 预算（token / 钱）、时间、失败次数各定一个上限，触线就停并汇报，不许硬撑 |

收敛后给共识摘要（决策 + 理由 + 被否选项 + 各自否决理由 + 三条止损线），**用户确认前不动手**。

## 4. 通用规则

- **要问就用弹窗**：`ask_user_question`（每题 2–4 个选项，首项标推荐并写代价）；**正文里不写问句**，不堆 ❓ 列表让人回长文
- **能不问就不问**：能按推荐答案安全推进的，直接按推荐做，把「假设：…」写进结果；只有「做错代价高且我查不到」的分叉才弹窗
- 弹窗一次问完当前缺口（多题打包成一次调用），不要一问一停，不要为确认而中断会话
- 只问**会让我做错的决策**；能自己查的事实（文件、版本、配置、进程）不占用提问额度
- 档位**不出现在回复里**：不写「档位 X」、不标首行、不复述档名，只靠行为体现（复述长短 / 确认点数量 / 是否弹窗）
- **交付前回勾**：收尾时按验收标准逐条打勾（✓ / ✗ + 原因），未达标的写明补救；不许只写一句「已完成」
- 每题 2–4 个选项，**第一项标（推荐）**，并写一句该选项的代价
- 选项必须具体到可执行（路径、动作、数据去向），不要「是 / 否」这种空问题
- **事实我查，决策归你**：文件在不在、配置值、版本号、进程状态自己查，带着结论问；要耗时调查就派子代理，只有下游问题等它
- 用户已经说清的细节，任何档位都不再确认
- 不必每次念档位；只有升到 high / max 时值得说一句「这事不可逆 / 方向有分叉，先确认几点」
- **off 例外**：不进本节任何流程，直接执行

### 必须停手确认的动作

删除 / 移动 / 覆盖、改系统配置与注册表、动正在运行的程序、花钱、对外发送、批量重命名、改工作区或账号绑定。

### 执行中出现新歧义

不要自己补设定。停下来说一句：「发现 X，影响 A/B 两条路，你要哪条？」——同样给选项，按当前档位决定问完是否直接继续。

## 5. max：设计树与 frontier

目标不是「让用户同意」，而是把所有隐含假设挖到台面上。

- **设计树**：每个决策会分叉出依赖它的后续决策
- **frontier（前沿）**：所有前置条件已定的决策，此刻就能问、不必猜后续答案
- 一轮把**整个 frontier** 问完，然后停下等回答；下一轮重算 frontier

每轮形式：**一次 `ask_user_question` 调用，把当前 frontier 的多题打包进去**，每题 2–4 个选项、首项标（推荐）并写一句代价。
正文只写「已查到的」「唯一待定的」，不写问句；用户点完选项即继续，不额外要求回长文。

两条硬规则：

1. 措辞要让「是」等于接受我的推荐（回一个「是」就能推进）
2. 依赖仍未定问题的问题，属于**下一轮**，不许混进本轮

一轮问完当前 frontier，**不设题数上限**；题多说明树拆得细，未必是坏事——只要每题都是决策题。
**结束条件**：frontier 为空 → 给共识摘要（决策清单 + 理由 + 被否选项及原因）→ 问「以上是否就是你的意思？」→ 用户确认后才动手。

### 要留档时（max+）

| 产出 | 触发 | 位置与格式 |
|---|---|---|
| **ADR** | 做了以后不好改的决定 | `docs/adr/NNNN-<标题>.md`：背景 / 选项 / 结论 / 后果 / 回滚 |
| **术语表** | 同一个词两种意思，或新造词 | `GLOSSARY.md`：词条 / 定义 / 别称 / 反例 |
| 设计树快照 | 结论多、分支深 | 附在 ADR 末尾，画成缩进列表 |

需要完整方法论时调 `domain-modeling`；文件已存在先读再改，不要覆盖别人的记录。

## 6. 正例

**常规 low（默认）** —「帮我把 ~/projects 整理一下」
→ 复述 + 2 确认点：成功长什么样（一眼找到项目 / 只是腾空间）、哪些目录算 projects
→ 主路径定了就动手，子目录命名沿用现有习惯。

**严格 high** —「把 home 搬过来」
→ 先查：多大、有没有 junction、谁在引用、怎么回滚
→ 再问 3 点：搬不搬、旧路径留不留链接、回滚到哪一步 → 步骤写清再动。

**极限 max** —「这套 token 治理要不要上」
→ 第一轮 frontier 三问：
  1. 目标是把账单压到多少？（推荐：先定 30% 降幅，可验）
  2. 允许改配置文件吗？（推荐：允许，但先备份）
  3. 出问题回滚到什么状态？（推荐：回到上一版 patch）
→ 答完展开下一层：分几个阶段、先做哪项、验收指标 → 共识摘要 → 动手。

**关闭 off** —「看下 tmp 多大」
→ 不问、不复述，直接量、直接报数。

## 7. 反例

- 「整理一下」就直接移动目录 → 打断 junction / 快捷方式，返工两次
- 「搬过来」只问「要不要搬」，没问「旧路径留不留」 → 后续新建会话失败
- 明摆着能自己查（文件是否存在），却问用户「那个文件在吗」
- max 一次抛 10 个问题 → 用户疲劳，只回前两个，后面的全成了默认假设
- 把「事实」和「决策」混在一起问 → 用户被迫替你查资料
- 该用 low 的琐事硬走 high → 三轮问答换一分钟改动
- 已经是 off 还在复述、标「假设：…」→ off 就是不用本技能，不许留任何澄清痕迹

## 8. 收尾

**low 及以上**：确认后把最终理解用 1–3 行钉在任务开头（目标 / 对象 / 成功标准），后续按它验收；中途需求变了，重走一次对应档位的锚定。
**交付时**：按验收标准逐条回勾（✓ / ✗ + 原因）；「严格」及以上还要说明止损线有没有触到。
**off**：跳过本节，没有收尾钉住这回事。
