# 对抗审方法（含三个真实翻车样例）

> 样例全部来自 `dsh-clarify-tier` 自己的事故，不是编的。每条格式即「攻击卡」：`隐患 | 触发条件 | 后果 | 检查方法`。

## 一、六轴矩阵为什么是这六轴

这六轴是从事故里归纳的，不是通用清单。新项目照抄前先换轴——**轴的来源应该是该项目的翻车史**。

| 轴 | 来源 |
|---|---|
| 版本 / 环境 | 本机两套 DSH（官方 0.2.1-rc.2 / NEXT 2.0.18），API 差异真实咬过人 |
| 机器状态 | 双实例同开 → 端口互顶（43871/EADDRINUSE） |
| 用户用法 | 清缓存、双窗口、连点 |
| 数据形态 | 坏 JSON、旧 schema、100 会话上限 |
| 时序 | 启动瞬间（端口未就绪）、重启中、断线 |
| 极端量 | 1000 文件、一次 50 条 |

## 二、三个样例

### 样例 1 · 1.4.2 假日志（2026-10-24）

- **改前**：端口退让时，日志同时打「桥接就绪 …:43871」和「…:43872」，且单个端口被占就喊「控件会退化为只读」。
- **判据**：端口被占时能自动退让，且日志如实反映。
- **应有的攻击**：
  - A1 `同一 server 重试 listen，旧回调会不会一起触发？ | Node 在失败后再次 listen | 日志/选端口被写成旧值 | 占住 43991 跑一次，看日志出现几条「就绪」`
  - A2 `「退化为只读」的条件写对了吗？ | 只有一个端口被占 | 误报，把人带偏 | 构造单端口占用，断言不出现该句`
- **当时怎么发现的**：读启动日志，发现两条「就绪」。
- **有对抗审能省**：一次「回退修复 → 测试变红」的验证（约 10 分钟）+ 一次误导排查。

### 样例 2 · 1.5.0 认领信号被自己污染（2026-10-24）

- **改前**：两套 DSH 都跑插件时，客户端用「本实例状态文件里有没有这个会话」认领实例；客户端写盘也会写这个会话。
- **判据**：两套同开时不串档。
- **应有的攻击**：
  - A1 `客户端自己也会写这个会话，会不会把对方的文件写成「认识」？ | 误连后用户点一下 | 两个实例都认领 → 信号永久失效 | 手工往对方状态文件 POST 一次，再查两边 knownSession`
  - A2 `刚打开、还没发消息的新会话，两边都不认识，怎么办？ | 首次打开 | 读到的可能是另一套的档位 | 清缓存后开第二套，看控件显示谁的值`
- **当时怎么发现的**：netstat 看到官方渲染进程连到 NEXT 的桥。
- **有对抗审能省**：1.5.1（owner 标记）+ 1.5.2（轮询）+ 1.5.3（认不准就不碰桥）三个版本，两轮重启。

### 样例 3 · 1.6.0 过度设计（2026-10-24）

- **改前**：用户说「把关闭换成常规」，实现成「最低档改为真轻档（low，带复述/确认点/假设清单）」。
- **判据**：第一格文案变成「常规」。
- **应有的攻击**：
  - A1 `用户说的是改显示还是改行为？ | 需求只有一句「换成常规」 | 语义被改，多做一版 + 回滚 | 动手前一句话确认：行为要不要跟着变`
  - A2 `旧状态里的 off 值怎么办？ | 已有 20 个会话 | 档位丢失/跳档 | 读状态文件统计 off 条数，重启前后对比`
- **当时怎么发现的**：用户下一句「只是名字改哦」。
- **有对抗审能省**：1.6.0 → revert → 1.6.1 三次提交与一次推送。

## 三、命中演练（要求 ≥2/3）

把上面三个样例的「改前状态 + 判据」交给一个不看结论的审查者，让它按本方法出攻击卡。

**2026-10-24 首轮实测（fresh 子代理，只给方法 + 三个改前状态 + 判据）**：出 15 条攻击，**3/3 命中已知根因**。

| 样例 | 命中的攻击 | 对应真实根因 |
|---|---|---|
| 1.4.2 | A4「日志端口取值来源/写入时机不对」 | 重试 listen 的旧回调把端口写错 |
| 1.5.0 | A1「认领只在写路径、读路径没有归属」、A2「同一 session id 出现在两个文件时优先级未定义」、A3「端口探测只验活着不验身份」 | 空窗读到对方档位 / 客户端写污染认领 / 只认 plugin 标记分不出实例 |
| 1.6.0 | A3「文案与内部值语义分叉」、A4「与既有『常规』术语撞名」 | 把改名做成语义改动 / 需求歧义没澄清 |

其余 11 条的处置（我自己分档，不是独立结论）：8 条判为**合理风险，进待验或边界**（如 TIME_WAIT 残留、端口段被第三方占用、状态文件并发写、DPI 截断）；3 条判为**过虑或不适用**（本机无 i18n 词条、防火墙策略未开、单实例无残留冲突）。

低于 2/3 就要改方法（改矩阵或改句式），不许直接放行。

## 四、三态判定为什么必须收口

悬空的担忧会一直挂在报告里，下一轮又要重新读一遍——成本高且没有结论。
「接受 / 驳回 / 转边界」三选一，保证每条攻击都有归宿：**能改的进改动，不能改的进边界文档**。

## 五、什么时候不该开

- 改文案、改错别字、补一行日志：评审就够。
- 判据本身还没定：先把判据写出来，再对抗。
- 预算已用完：排队到下一轮，不要偷偷加量。
