# 对抗审 · counter-review（v0.1）

把「评委」换成「反对者」：默认本轮结论**换个条件就会坏**，用固定场景矩阵去逼它现形。
不是找「现在错没错」（那是评审），是找「换个环境/换种用法会不会错」。

## 何时开

| 触发 | 动作 |
|---|---|
| `forge_level` 返回 `counter.enabled = true` | 在评审轮**开始前**跑一轮对抗审 |
| 用户说「杠我 / 找茬 / 会怎么坏 / 再想想」 | 任何档位都开，条数听用户的 |
| 每次交付前的最后一轮 | 至少跑 3 条（防「只在新场景才坏」的东西被放过） |

档位与预算（由 `forge_level.counter` 给出，不要自己改）：

| 循环档 | 开不开 | 每轮条数 | 什么时候 |
|---|---|---|---|
| 轻量（`lite`） | 关 | 0 | — |
| 交付（`high`） | 开 | ≤3 | 只在收敛轮 |
| 极致（`max`） | 开 | ≤5 | 第 2 轮起每轮 |

## 三条铁律

1. **只审本轮改动**（和判据里的硬伤项）。旧结论不翻，除非出现了矩阵里的新场景。
2. **每条攻击必须四元组**：`隐患 | 触发条件 | 后果 | 检查方法`。缺任意一项 → 直接作废，不许写进报告。
3. **三态收口**，不许悬空：
   - **接受** → 挂 D 号，进本轮改动；
   - **驳回** → 给证据（代码位置 / 实测输出 / 文档行），一行写清；
   - **转边界** → 记进「已知边界」，写清影响范围与代价，不修但说清。

## 六轴场景矩阵

每条改动至少在**一条轴**上被拷问一次；覆盖不到的轴写「Z（未涉及）」，不许留空。

| 轴 | 拷问什么 |
|---|---|
| 版本 / 环境 | 换一套 DSH（官方 vs NEXT）、换 Node 版本、换系统 |
| 机器状态 | 单实例 / 双实例 / 端口被占 / 没网 / 慢盘 |
| 用户用法 | 首次打开、清了缓存、连点、两个窗口同开、只读用户 |
| 数据形态 | 空数据、上限值（100 会话）、坏 JSON、旧 schema、超长字符串 |
| 时序 | 启动瞬间、重启中、断线、写盘失败、并发写 |
| 极端量 | 批量操作、一次 50 条、1000 个文件 |

## 攻击怎么问（「万一」句式）

- 万一他**根本不清理缓存**，我这套判断还成立吗？
- 万一**两套 DSH 同时开**，我会不会写到另一个实例？
- 万一**第一次打开、还没发过消息**，我的信号是空的吗？
- 万一**数据是坏的 / 空的 / 到上限**，我会崩还是静默降级？
- 万一**写到一半断电**，文件会半截吗？
- 万一**用户连点 20 下**，会不会并发写、互相覆盖？

一句话模板：

> 万一 **<触发条件>**，**<后果>**；检查方法：**<怎么验证或观察>**。

## 预算与止损（防杠精化）

- **硬上限**：按档位表，超出的攻击排队到下一轮，不展开。
- **泛化收敛**：连续 2 轮「零新攻击」→ 停止，报告写 `泛化收敛`。
- **作废规则**：说不出检查方法的攻击 → 作废；同一隐患重复提 → 记「已答复」，不重复计数。
- **不追风格**：命名、措辞、排版这类偏好不进对抗审（那是评审的事）。

## 输出块（照抄）

```
── 对抗审 ──
矩阵覆盖：版本 Y · 实例 Z · 用法 Y · 数据 Z · 时序 Y · 极端量 Z
A1 [接受] 双实例同开时控件可能连到另一套 → 挂 D7
A2 [驳回] 「旧内核不支持 SSE」→ 实测两套均 Chromium 128，支持
A3 [边界] 10 个端口全占时退化为只读 → 已写 README 已知边界
新增 3 · 接受 1 · 驳回 1 · 边界 1 · 重复 0
```

## 与 clarify-needs 的分工

| 技能 | 审什么 | 什么时候 |
|---|---|---|
| clarify-needs（max 档） | **方案**能不能扛住反对意见 | 动手前 |
| counter-review（本技能） | **改动**换个条件会不会坏 | 循环的每轮 |

矩阵、攻击卡、三态判定两处共用同一套定义，写在 `docs/method.md`，不再各写一份。

## 边界

- 不做需求评审、不做代码风格评审。
- 不承诺「保证大范围可用」：只输出**矩阵覆盖情况 + 已知边界清单**，两者都可核对。
- 攻击必须能被检查；「我觉得可能不行」一律作废。
