# counter-review · 对抗审

循环锻造里的「反对者」：每轮改动都问一遍「万一换个条件会怎样」，把「只在我这台机器上能用」的东西逼出来。

## 一句话

评审查「现在错没错」，对抗审只查「**换个环境/换种用法会不会错**」。

## 什么时候用

| 场景 | 用法 |
|---|---|
| 档位条右侧「对抗」亮着 | 思考模式=动手前审方案 + 交付前审改动；循环模式=每轮审改动 |
| 只是想把方案压一遍 | 直接说「杠我」「找茬」「会怎么坏」 |
| 交付前最后一轮 | 至少 3 条，防「新场景才坏」被放过 |

条数随档位：常规/严格 3 条、极致 5 条；关着=0 条。

## 输出长什么样

```
── 对抗审 ──
矩阵覆盖：版本 Y · 实例 Z · 用法 Y · 数据 Z · 时序 Y · 极端量 Z
A1 [接受] 双实例同开时控件可能连到另一套 → 挂 D7
A2 [驳回] 「旧内核不支持 SSE」→ 实测两套均 Chromium 128，支持
A3 [边界] 10 个端口全占时退化为只读 → 已写 README 已知边界
新增 3 · 接受 1 · 驳回 1 · 边界 1 · 重复 0
```

- **接受**：真问题，挂缺陷号，本轮就改。
- **驳回**：不成立，但必须给证据（代码位置 / 实测 / 文档行）。
- **转边界**：改不动或不该改，写进「已知边界」，说清影响范围与代价。

## 不做什么

- 不追风格、措辞、排版（评审的事）。
- 不做无边界的追问：每条必须有「检查方法」，否则作废。
- 不承诺「保证通用」：只交两样可核对的东西——**矩阵覆盖率**、**已知边界清单**。

## 配套

- 方法全文（含三个真实翻车样例）：`docs/method.md`
- 与 `clarify-needs` 的分工：它动手前审方案，本技能每轮审改动，共用同一套矩阵与判定。
- 由插件 `dsh-clarify-tier` 的 `forge_level.counter` 字段开关。
